\section{Experimental Methodology}

\subsection{Part 1 -- Cache Benchmarks}

Every timing-only reverse-engineering target in this project -- cache-level/capacity
discovery, line size, associativity, hit latency, miss/next-level latency, and
inclusion/exclusion behavior (Section~\ref{sec:phase1}) -- is built from one shared
measurement primitive implemented once in \texttt{main\_code/common/} and compiled into a
single portable command-line tool, \texttt{cache\_bench}
(\texttt{main\_code/common/main.c}). Every experiment differs only in \emph{which}
parameter it sweeps and how it lays out the pointer-chase graph; the load, timing, and
batching machinery underneath is identical across all six targets and is described once
here so later subsections can point back to a listing number instead of repeating it, per
the reused-common-code convention required for this report.

\subsubsection{Dependent Pointer-Chase Primitive}

Every measurement in this codebase is built around a single dependent load chain: a
singly-linked cycle of fixed-size nodes, each holding only a \texttt{next} pointer, laid
out over a working-set buffer of controlled size and node spacing. Because the address of
load $i+1$ is the \emph{value} produced by load $i$, the CPU cannot issue, prefetch, or
reorder load $i+1$ before load $i$ completes -- this is what isolates true load-to-use
cache/TLB latency instead of memory bandwidth or issue-width effects. Listing~\ref{lst:pchase}
shows the whole primitive; it is architecture-independent and is reused, unmodified, by
every experiment in Section~\ref{sec:phase1}.

\begin{lstlisting}[caption={Dependent pointer-chase primitive (portable, all architectures). File: \texttt{main\_code/common/pointer\_chase.h} / \texttt{pointer\_chase.c}, commit \texttt{e0f2538}.},label={lst:pchase}]
#ifndef POINTER_CHASE_H
#define POINTER_CHASE_H

#include <stdint.h>

struct node {
    struct node *next;
};

void chase(struct node *p, uint64_t steps);

#endif

/* ---- pointer_chase.c ---- */
#include "pointer_chase.h"

static volatile struct node *sink_node;

void chase(struct node *p, uint64_t steps) {
    for (uint64_t i = 0; i < steps; i++) {
        p = p->next; /* next address depends on previous load */
    }
    sink_node = p; /* keep the final result observable */
}
\end{lstlisting}

The result of the final load is stashed in a \texttt{volatile} sink so the compiler cannot
prove the whole loop is dead and eliminate it -- necessary discipline even at the
\texttt{-O0} baseline used throughout this project (Section~\ref{sec:build}).

\subsubsection{Timing: Serialized Cycle Counters (x86-64 and AArch64)}

Every experiment measures elapsed time in raw CPU cycles ("ticks") via a portable
\texttt{timer\_start()}/\texttt{timer\_stop()} pair that dispatches, at compile time, to an
architecture-specific implementation (Listing~\ref{lst:timer}). This is the \emph{only}
architecture-specific code in the entire codebase -- every experiment-specific file
(Section~\ref{sec:phase1}) calls only the portable \texttt{timer.h} interface and requires
zero changes to run on Sunbird/Skylark/Crux/Ookay/Upgrade/Charnwood/Artemisia (x86-64) or
Thunderbird (AArch64).

\begin{lstlisting}[caption={Portable timer dispatch. File: \texttt{main\_code/common/timer.h}, commit \texttt{e0f2538}.},label={lst:timer}]
#ifndef TIMER_H
#define TIMER_H

#include <stdint.h>

#if defined(__x86_64__) || defined(__i386__)

#include "../x86_64/timer_x86.h"

static inline uint64_t timer_start(void){
    return x86_tsc_start();
}

static inline uint64_t timer_stop(void){
    return x86_tsc_stop();
}

#elif defined(__aarch64__)

#include "../aarch64/timer_arm.h"

static inline uint64_t timer_start(void){
    return arm_counter_start();
}

static inline uint64_t timer_stop(void){
    return arm_counter_stop();
}

#else

#error "Unsupported architecture"

#endif

#endif
\end{lstlisting}

On x86-64 (Listing~\ref{lst:timerx86}), \texttt{timer\_start()} issues \texttt{LFENCE}
before \texttt{RDTSC} to drain in-flight instructions so the cycle read is not reordered
ahead of the code it is meant to time, and \texttt{timer\_stop()} uses the partially
self-serializing \texttt{RDTSCP} (which also drains prior instructions before reading the
counter) followed by a further \texttt{LFENCE} to prevent the \emph{next} region's
instructions from being reordered backward into the timed window.

\begin{lstlisting}[caption={x86-64 serialized TSC timer. File: \texttt{main\_code/x86\_64/timer\_x86.h}, commit \texttt{e0f2538}. Target architecture: x86-64.},label={lst:timerx86}]
#include <stdint.h>
#include <x86intrin.h>

static inline uint64_t x86_tsc_start(void) {
    _mm_lfence();
    uint64_t t = __rdtsc();
    _mm_lfence();
    return t;
}

static inline uint64_t x86_tsc_stop(void) {
    unsigned aux;
    uint64_t t = __rdtscp(&aux);
    _mm_lfence();
    return t;
}

static inline uint64_t time_one_load(volatile const uint64_t *p) {
    uint64_t t0 = x86_tsc_start();
    uint64_t value = *p;
    uint64_t t1 = x86_tsc_stop();
    __asm__ __volatile__("" : "+r"(value) :: "memory");
    return t1 - t0;
}
\end{lstlisting}

On AArch64 (Listing~\ref{lst:timerarm}), the free-running virtual counter
\texttt{CNTVCT\_EL0} is read between \texttt{DSB SY}/\texttt{ISB} barrier pairs, which
serialize the instruction stream in the same role \texttt{LFENCE} plays on x86. A real
resolution limitation surfaced on Thunderbird (Ampere Q80-30, Neoverse N1):
\texttt{CNTFRQ\_EL0} reports only 25\,MHz, so ticks/access for the whole 1\,KiB--1\,GiB
capacity range span roughly 0.08--2.4 -- below the x86-calibrated automatic boundary/knee
detectors' default absolute-tick thresholds (Sections~\ref{sec:capacity} and
\ref{sec:assoc}), which had to be rescaled per-machine on this ISA rather than reused
as-is.

\begin{lstlisting}[caption={AArch64 serialized virtual-counter timer. File: \texttt{main\_code/aarch64/timer\_arm.h}, commit \texttt{e0f2538}. Target architecture: AArch64.},label={lst:timerarm}]
#include <stdint.h>
static inline uint64_t arm_counter_start(void) {
    uint64_t t;
    __asm__ __volatile__(
        "dsb sy\n\t"
        "isb\n\t"
        "mrs %0, cntvct_el0\n\t"
        "isb\n\t"
        : "=r"(t) :: "memory");
    return t;
}

static inline uint64_t arm_counter_stop(void) {
    uint64_t t;
    __asm__ __volatile__(
        "dsb sy\n\t"
        "isb\n\t"
        "mrs %0, cntvct_el0\n\t"
        "isb\n\t"
        : "=r"(t) :: "memory");
return t;
}

static inline uint64_t arm_counter_freq(void) {
    uint64_t f;
    __asm__ __volatile__("mrs %0, cntfrq_el0" : "=r"(f));
    return f;
}
\end{lstlisting}

\subsubsection{Batched Measurement and Statistical Discipline}
\label{sec:batching}

A single \texttt{timer\_start()}/\texttt{timer\_stop()} pair carries tens of ticks of fixed
overhead (quantified directly in Section~\ref{sec:misslatency}), so every experiment except
miss/inclusion latency (which are inherently single-shot, Sections~\ref{sec:misslatency}
and~\ref{sec:inclusion}) times a \emph{batch} of $B$ back-to-back dependent accesses as one
region and reports the batch average, amortizing that fixed cost across $B{=}1000$
accesses by default. Batching this way -- rather than reporting one grand mean per
working-set size -- preserves the per-batch distribution, which downstream repeat-run and
box-plot analysis (Sections~\ref{sec:capacity}--\ref{sec:inclusion}) depends on to tell a
genuine cache-level transition apart from run-to-run system noise. The
\texttt{>= 1{,}000{,}000} timed-access-per-point requirement is enforced structurally, not
by convention: \texttt{num\_batches} is computed by ceiling division of
\texttt{samples}/\texttt{batch\_size}, and untimed warm-up passes never write into the
latency array that is later printed, so a warm-up access can never be miscounted as a timed
sample. Listing~\ref{lst:benchmark} also shows the required independent-load control used
by the hit-latency experiment (Section~\ref{sec:hitlatency}): each load's address is drawn
from a precomputed permutation instead of the previous load's result, which exposes
memory-level parallelism (MLP) and is expected to read \emph{faster} than the dependent
chain at the same footprint -- this is the mechanism the assignment's MLP sanity check
relies on.

\begin{lstlisting}[caption={Batched dependent and independent load timers (portable). File: \texttt{main\_code/common/benchmark.h} / \texttt{benchmark.c}, commit \texttt{e343732}.},label={lst:benchmark}]
void measure_dependency_chain_batched(struct node *start,
                                       uint64_t batch_size,
                                       size_t num_batches,
                                       double *out_latencies);

void measure_independent_loads_batched(struct node *nodes,
                                        const size_t *order,
                                        size_t order_len,
                                        uint64_t batch_size,
                                        size_t num_batches,
                                        double *out_latencies);

/* ---- benchmark.c ---- */
static volatile struct node *bench_sink;

void measure_dependency_chain_batched(struct node *start,
                                       uint64_t batch_size,
                                       size_t num_batches,
                                       double *out_latencies)
{
    struct node *p = start;

    for (size_t b = 0; b < num_batches; b++) {
        uint64_t t0 = timer_start();
        for (uint64_t i = 0; i < batch_size; i++) {
            p = p->next; /* next address depends on previous load */
        }
        uint64_t t1 = timer_stop();
        out_latencies[b] = (double)(t1 - t0) / (double)batch_size;
    }

    bench_sink = p; /* keep the final result observable */
}

void measure_independent_loads_batched(struct node *nodes,
                                        const size_t *order,
                                        size_t order_len,
                                        uint64_t batch_size,
                                        size_t num_batches,
                                        double *out_latencies)
{
    struct node *last = NULL;
    size_t idx = 0;

    for (size_t b = 0; b < num_batches; b++) {
        uint64_t t0 = timer_start();
        for (uint64_t i = 0; i < batch_size; i++) {
            /* Address comes from the caller-supplied permutation, not from
             * the value just loaded -- unlike measure_dependency_chain_batched(),
             * nothing here forces one load to wait on the previous one. */
            last = nodes[order[idx]].next;
            idx++;
            if (idx == order_len) {
                idx = 0;
            }
        }
        uint64_t t1 = timer_stop();
        out_latencies[b] = (double)(t1 - t0) / (double)batch_size;
    }

    bench_sink = last; /* keep the final result observable */
}
\end{lstlisting}

\subsubsection{Access-Pattern Construction: Randomized vs.\ Sequential Control}

Every experiment builds its dependent cycle one of two ways (Listing~\ref{lst:random}):
\texttt{make\_random\_cycle\_strided()} performs a seeded Fisher--Yates shuffle (using a
32-bit xorshift PRNG) over the node indices and links them in that shuffled order, so
consecutive accesses land at pseudo-random offsets a hardware stride prefetcher cannot
predict; \texttt{make\_sequential\_cycle\_strided()} links nodes in plain array order, a
fully stride-predictable control. Every capacity, line-size, and associativity sweep in
this project (Section~\ref{sec:phase1}) is run at \emph{both} patterns over the same swept
range: if a detected transition also appears, unchanged, on the sequential control, it is
a prefetcher or fixed-overhead artifact rather than a genuine cache-capacity/line-size/
associativity effect, and is discounted. The \emph{strided} variants generalize node
spacing beyond \texttt{sizeof(struct node)}, which is what lets the same construction be
reused unmodified for line size (spacing = candidate line size, Section~\ref{sec:linesize})
and associativity (spacing = a cache level's own confirmed capacity,
Section~\ref{sec:assoc}).

\begin{lstlisting}[caption={PRNG, shuffle, and cycle construction (portable). File: \texttt{main\_code/common/random.h} / \texttt{random.c}, commit \texttt{e343732}.},label={lst:random}]
uint32_t xorshift32(uint32_t *state) {
    uint32_t x = *state;
    x ^= x << 13;
    x ^= x >> 17;
    x ^= x << 5;
    return *state = x;
}

static struct node *node_at(void *base, size_t i, size_t stride) {
    return (struct node *)((uint8_t *)base + i * stride);
}

void make_random_cycle_strided(void *base, size_t n, size_t stride, uint32_t seed) {
    size_t *order = malloc(n * sizeof(*order));
    if (!order || n < 2) exit(1);
    for (size_t i = 0; i < n; i++) order[i] = i;

    uint32_t state = seed ? seed : 1u;
    for (size_t i = n - 1; i > 0; i--) {
        size_t j = (size_t)(xorshift32(&state) % (uint32_t)(i + 1));
        size_t tmp = order[i];
        order[i] = order[j];
        order[j] = tmp;
    }
    for (size_t i = 0; i < n; i++)
        node_at(base, order[i], stride)->next = node_at(base, order[(i + 1) % n], stride);
    free(order);
}

void make_sequential_cycle_strided(void *base, size_t n, size_t stride) {
    if (n < 2) exit(1);
    for (size_t i = 0; i < n; i++)
        node_at(base, i, stride)->next = node_at(base, (i + 1) % n, stride);
}

void make_random_cycle(struct node *nodes, size_t n, uint32_t seed) {
    make_random_cycle_strided(nodes, n, sizeof(struct node), seed);
}

void make_sequential_cycle(struct node *nodes, size_t n) {
    make_sequential_cycle_strided(nodes, n, sizeof(struct node));
}

size_t *make_shuffled_indices(size_t n, uint32_t seed) {
    size_t *order = malloc(n * sizeof(*order));
    if (!order || n < 1) exit(1);
    for (size_t i = 0; i < n; i++) order[i] = i;

    uint32_t state = seed ? seed : 1u;
    for (size_t i = n - 1; i > 0; i--) {
        size_t j = (size_t)(xorshift32(&state) % (uint32_t)(i + 1));
        size_t tmp = order[i];
        order[i] = order[j];
        order[j] = tmp;
    }
    return order;
}
\end{lstlisting}

\subsubsection{Build Configuration and the \texttt{cache\_bench} Driver}
\label{sec:build}

All six experiments are compiled with one fixed baseline (Listing~\ref{lst:makefile}):
\texttt{-O0 -g -std=c11 -Wall -Wextra -fno-omit-frame-pointer}. \texttt{-O0} is deliberate,
not just conservative -- the entire method depends on the compiler emitting one genuine
load per loop iteration in \texttt{chase()} / \texttt{measure\_dependency\_chain\_batched()}
(Listings~\ref{lst:pchase},~\ref{lst:benchmark}); any optimization pass that hoisted,
vectorized, or reordered those loads would silently break the intentional dependency the
whole technique relies on. \texttt{-g}/\texttt{-fno-omit-frame-pointer} are kept so the
emitted code can be inspected in a disassembly listing as evidence that the dependency
survives compilation -- a check flagged as still outstanding on Sunbird as of this
writing (see \texttt{data\_raw/sunbird/README.md}).

\subsection{Machine Access, Core Pinning, and Phase Discipline}
\label{sec:phasediscipline}

Every \texttt{cache\_bench} invocation is pinned to a single physical core with
\texttt{taskset -c <core>} on the ECE lab machines, or \texttt{srun --cpu-bind=cores} on
the Hazel HPC cluster (Section~\ref{sec:hazel}). Before pinning, \texttt{Cpus\_allowed\_list}
and \texttt{lscpu -e=CPU,CORE,SOCKET,NODE} were checked to identify a full physical core
(both SMT siblings) actually available to the session, and \texttt{ps}/other-user activity
was checked to avoid a core another student was actively using. A single point-in-time
\texttt{ps} snapshot was found to be insufficient on at least one shared machine (Artemisia)
-- per-core load moved visibly across three consecutive 6-second sampling windows taken
seconds apart -- so idle-core selection there was instead based on \texttt{/proc/stat}
idle-time deltas sampled over multiple windows.

Long dense sweeps (working sets of $\gtrsim$100\,MiB at the random pattern) cost real wall
time, since random-pattern latency at that scale is dominated by genuine uncached DRAM
access; a full sweep at the default sample count can take on the order of an hour. Any run
in this range was launched inside a detached \texttt{tmux} session so it would survive the
driving terminal session disconnecting, with a second \texttt{tmux} session used purely to
poll for completion when needed -- a background-task watcher tied to an interactive session
does not itself survive that session ending, only a process actually backgrounded on the
machine (via \texttt{tmux}) does. Raw per-batch CSVs are gzip-compressed before being
committed (\texttt{data\_raw/<machine>/<experiment>/*.csv.gz}) to keep the repository size
tractable across eight machines' worth of million-sample sweeps.

One further methodological pitfall, confirmed on Sunbird, is worth stating explicitly: a
dense sweep started exactly at the left edge of the working-set range of interest can show
a spurious plateau caused by CPU frequency/P-state ramp-up (the first several points run
before the core reaches steady-state turbo clock), which decays over the first few dozen
points and is not a cache effect. Every dense sweep in this project accordingly starts
meaningfully below its region of actual interest rather than exactly at its boundary.

Finally, this project follows a strict three-phase discipline, stated in full in the
repository \texttt{README.md} and enforced by a frozen, tagged commit
(\texttt{phase1-timing-only}) before Phase II may begin:
\begin{itemize}
    \item \textbf{Phase I -- timing only} (this section and Section~\ref{sec:phase1}): no
    \texttt{perf}, no PMU, no cache-topology files, no vendor cache tables or published
    specifications used to \emph{derive} an inferred value -- every boundary, line size,
    associativity, and latency number reported in Section~\ref{sec:phase1} is inferred from
    timing measurements alone.
    \item \textbf{Phase II -- counter and literature verification} (Section~\ref{sec:pmu}):
    only entered after Phase I is tagged.
    \item \textbf{Phase III -- Hazel} (Section~\ref{sec:hazel}): a lab-only prediction is
    frozen and committed \emph{before} any cache experiment is run on Hazel.
\end{itemize}
Every experiment's exact build command, run command, compiler flags, core affinity, timer
method, sample count, seed, and raw-output filenames are recorded per machine in
\texttt{data\_raw/<machine>/README.md}, and every reduction step from raw CSV to processed
summary to plot is a checked-in script under \texttt{scripts/} (Section~\ref{sec:phase1}
lists the one used per target) -- together these are sufficient to reproduce every result
in Section~\ref{sec:phase1} from the raw data alone.

\section{Timing-Only Cache Reverse Engineering}
\label{sec:phase1}

Each subsection below follows the same chain: the access pattern and swept parameter
(built from the common code in Section~\ref{sec:build}) $\rightarrow$ the controlled sweep
$\rightarrow$ the measured distribution/plot $\rightarrow$ the inference rule applied to it
$\rightarrow$ its current Phase-II validation status. Full per-machine numeric results
(all eight machines) are tabulated in Section~\ref{sec:evolution} and in each machine's own
\texttt{data\_processed/<machine>/FINAL\_CACHE\_TABLE.md}; this section illustrates the
method itself, using Sunbird (the most complete single-machine dataset) as the running
example unless noted otherwise.

\subsection{Cache Hierarchy and Capacity}
\label{sec:capacity}

\textbf{What is varied:} working-set footprint $N$, log-spaced (8 points/octave by
default) from 1\,KiB up to a coarse ceiling (64\,MiB by default, extended manually to
1\,GiB when the topmost region has not yet plateaued). \textbf{What is held constant:}
node size, batch size, seed, warm-up passes, core pinning. \textbf{What is measured:}
median ticks/access per footprint, at both the random and sequential access patterns.
Listing~\ref{lst:capacity} is the complete implementation: for each swept size it builds a
fresh dependent cycle sized to exactly fill that footprint, runs the required warm-up
passes untimed, then times \texttt{num\_batches} batches via
\texttt{measure\_dependency\_chain\_batched()} (Listing~\ref{lst:benchmark}) and prints one
raw CSV row per (size, batch).

\begin{lstlisting}[caption={Cache-level/capacity discovery. Target property: cache-level boundaries (L1/L2/LLC/DRAM). Architecture: portable common code (compiled for both x86-64 and AArch64 via Listing~\ref{lst:timer}). File: \texttt{main\_code/common/capacity.c}, commit \texttt{8fb1467}.},label={lst:capacity}]
int run_capacity_experiment(const struct capacity_config *cfg)
{
    uint64_t min_bytes = cfg->min_bytes;
    if (min_bytes < sizeof(struct node) * 2) {
        min_bytes = sizeof(struct node) * 2;
    }

    uint64_t num_batches = (cfg->samples + cfg->batch_size - 1) / cfg->batch_size;
    if (num_batches < 1) {
        num_batches = 1;
    }
    uint64_t achieved_samples = num_batches * cfg->batch_size;

    double *batch_latencies = malloc(num_batches * sizeof(double));
    if (batch_latencies == NULL) {
        fprintf(stderr, "allocation failed for %" PRIu64 " batch samples\n", num_batches);
        return 1;
    }

    const char *pattern_name =
        (cfg->pattern == ACCESS_PATTERN_SEQUENTIAL) ? "sequential" : "random";

    printf("size_bytes,num_nodes,pattern,batch_index,avg_ticks_per_access\n");

    size_t last_num_nodes = 0;
    double step = 1.0 / (double)cfg->points_per_octave;
    double log2_min = log2((double)min_bytes);
    double log2_max = log2((double)cfg->max_bytes);

    for (double exp = log2_min; exp <= log2_max + 1e-9; exp += step) {
        uint64_t bytes = (uint64_t)(pow(2.0, exp) + 0.5);
        size_t num_nodes = (size_t)(bytes / sizeof(struct node));
        if (num_nodes < 2) num_nodes = 2;
        if (num_nodes == last_num_nodes) continue;
        last_num_nodes = num_nodes;

        struct node *nodes = malloc(num_nodes * sizeof(struct node));
        if (nodes == NULL) { free(batch_latencies); return 1; }

        if (cfg->pattern == ACCESS_PATTERN_SEQUENTIAL) {
            make_sequential_cycle(nodes, num_nodes);
        } else {
            make_random_cycle(nodes, num_nodes, cfg->seed);
        }

        /* Untimed pass(es): fault in pages and settle steady-state
         * residency for this working-set size before timing starts. */
        for (int w = 0; w < cfg->warmup_passes; w++) {
            chase(nodes, (uint64_t)num_nodes);
        }

        measure_dependency_chain_batched(nodes, cfg->batch_size, num_batches,
                                          batch_latencies);

        uint64_t size_bytes = (uint64_t)num_nodes * sizeof(struct node);
        for (uint64_t b = 0; b < num_batches; b++) {
            printf("%" PRIu64 ",%zu,%s,%" PRIu64 ",%.4f\n",
                   size_bytes, num_nodes, pattern_name, b, batch_latencies[b]);
        }
        fflush(stdout);
        free(nodes);
    }
    free(batch_latencies);
    return 0;
}
\end{lstlisting}

Raw per-batch CSVs are reduced by \texttt{scripts/summarize\_raw.py} into one
distribution-stats row per (size, pattern), then \texttt{scripts/detect\_cache\_hierarchy.py}
scans consecutive size points for a sustained tick jump exceeding both an absolute and a
relative threshold to flag a boundary, and \texttt{scripts/plot\_capacity.py} renders the
curve. \texttt{scripts/run\_capacity\_full.sh <machine> <core>} chains coarse sweep
$\rightarrow$ automatic boundary detection $\rightarrow$ per-boundary dense sweep
$\rightarrow$ reproducibility repeats $\rightarrow$ tail-extension sweep $\rightarrow$
plots into one command.

\subsection{Cache Line Size}
\label{sec:linesize}

\textbf{What is varied:} either the byte stride between nodes at a fixed footprint
(single-curve method), or the working-set footprint at one fixed candidate stride,
repeated once per candidate stride (family-of-curves method, PROJECT 1.pdf Figure 3 /
"Example B"). \textbf{What is held constant:} in each method, the parameter not being
swept, plus buffer base alignment (recorded, not swept, in the single-curve method; also
swept as a sub-line \texttt{offset\_bytes} cross-check in the family method).
\textbf{What is measured:} median ticks/access at each stride or footprint point, random
and sequential. Listing~\ref{lst:linesize} implements both methods in one file.

\begin{lstlisting}[caption={Cache line size, both independent methods. Target property: cache line size. Architecture: portable common code. File: \texttt{main\_code/common/line\_size.c}, commit \texttt{1689b22}.},label={lst:linesize}]
/* ---- single-curve method: fixed footprint, stride swept ---- */
int run_line_size_experiment(const struct line_size_config *cfg)
{
    uint64_t min_stride = cfg->min_stride;
    if (min_stride < sizeof(struct node)) min_stride = sizeof(struct node);

    uint64_t num_batches = (cfg->samples + cfg->batch_size - 1) / cfg->batch_size;
    if (num_batches < 1) num_batches = 1;

    double *batch_latencies = malloc(num_batches * sizeof(double));
    if (batch_latencies == NULL) return 1;

    const char *pattern_name =
        (cfg->pattern == ACCESS_PATTERN_SEQUENTIAL) ? "sequential" : "random";

    printf("stride_bytes,num_nodes,footprint_bytes,align_bytes,pattern,batch_index,avg_ticks_per_access\n");

    for (uint64_t stride = min_stride; stride <= cfg->max_stride; stride += cfg->stride_step) {
        size_t num_nodes = (size_t)(cfg->footprint_bytes / stride);
        if (num_nodes < 2) { continue; } /* stride too large for this footprint */

        uint64_t buffer_bytes = (uint64_t)(num_nodes - 1) * stride + sizeof(struct node);
        void *base = NULL;
        if (posix_memalign(&base, (size_t)cfg->align_bytes, (size_t)buffer_bytes) != 0) {
            free(batch_latencies); return 1;
        }

        if (cfg->pattern == ACCESS_PATTERN_SEQUENTIAL) {
            make_sequential_cycle_strided(base, num_nodes, (size_t)stride);
        } else {
            make_random_cycle_strided(base, num_nodes, (size_t)stride, cfg->seed);
        }

        for (int w = 0; w < cfg->warmup_passes; w++) chase(base, (uint64_t)num_nodes);
        measure_dependency_chain_batched(base, cfg->batch_size, num_batches, batch_latencies);

        for (uint64_t b = 0; b < num_batches; b++) {
            printf("%" PRIu64 ",%zu,%" PRIu64 ",%" PRIu64 ",%s,%" PRIu64 ",%.4f\n",
                   stride, num_nodes, cfg->footprint_bytes, cfg->align_bytes,
                   pattern_name, b, batch_latencies[b]);
        }
        fflush(stdout);
        free(base);
    }
    free(batch_latencies);
    return 0;
}

\subsection{Cache Associativity}
\label{sec:assoc}

\textbf{What is varied:} the number of same-set nodes chased in one dependent cycle
(\texttt{num\_ways}), from \texttt{min\_ways} to \texttt{max\_ways}. \textbf{What is held
constant:} the node-to-node stride, fixed at \texttt{cache\_bytes} -- the target cache
level's own confirmed capacity from \texttt{CAPACITY\_RESULTS.md} -- so every probed node
lands in the same cache set by construction, but carries a distinct tag.
\textbf{What is measured:} median ticks/access per \texttt{num\_ways}.

\begin{lstlisting}[caption={Cache associativity (way count per set), including the huge-page DTLB-control diagnostic. Target property: associativity. Architecture: portable common code. File: \texttt{main\_code/common/associativity.c}, commit \texttt{22104d6}.},label={lst:assoc}]
int run_associativity_experiment(const struct associativity_config *cfg)
{
    uint64_t min_ways = cfg->min_ways < 2 ? 2 : cfg->min_ways;
    uint64_t num_batches = (cfg->samples + cfg->batch_size - 1) / cfg->batch_size;
    if (num_batches < 1) num_batches = 1;

    double *batch_latencies = malloc(num_batches * sizeof(double));
    if (batch_latencies == NULL) return 1;

    const char *pattern_name =
        (cfg->pattern == ACCESS_PATTERN_SEQUENTIAL) ? "sequential" : "random";

    printf("num_ways_probed,cache_bytes,pattern,batch_index,avg_ticks_per_access\n");

    for (uint64_t num_ways = min_ways; num_ways <= cfg->max_ways; num_ways += cfg->way_step) {
        /* Every node is cfg->cache_bytes apart, so the touched address range
         * spans (num_ways - 1) strides plus one node. */
        uint64_t buffer_bytes = (num_ways - 1) * cfg->cache_bytes + sizeof(struct node);

        void *base = NULL;
        if (cfg->huge_pages) {
            /* 2 MiB-align via mmap(), madvise(MADV_HUGEPAGE), fault in every
             * 4 KiB page -- collapses the whole probe buffer onto a SINGLE
             * TLB entry regardless of num_ways, directly testing whether an
             * observed knee is a TLB/page-boundary artifact rather than a
             * real cache-set limit. Actual backing achieved is confirmed
             * from /proc/self/smaps's AnonHugePages field, not assumed from
             * a successful madvise() call. See report_huge_page_backing()
             * in main_code/common/associativity.c for the full diagnostic. */
            base = alloc_huge_page_aligned(buffer_bytes); /* see full source */
        } else {
            base = malloc((size_t)buffer_bytes);
        }
        if (base == NULL) { free(batch_latencies); return 1; }

        if (cfg->pattern == ACCESS_PATTERN_SEQUENTIAL) {
            make_sequential_cycle_strided(base, (size_t)num_ways, (size_t)cfg->cache_bytes);
        } else {
            make_random_cycle_strided(base, (size_t)num_ways, (size_t)cfg->cache_bytes, cfg->seed);
        }

        for (int w = 0; w < cfg->warmup_passes; w++) chase(base, num_ways);
        measure_dependency_chain_batched(base, cfg->batch_size, num_batches, batch_latencies);

        for (uint64_t b = 0; b < num_batches; b++) {
            printf("%" PRIu64 ",%" PRIu64 ",%s,%" PRIu64 ",%.4f\n",
                   num_ways, cfg->cache_bytes, pattern_name, b, batch_latencies[b]);
        }
        fflush(stdout);
        free_probe_buffer(base, cfg->huge_pages);
    }
    free(batch_latencies);
    return 0;
}

\textbf{Phase-II validation and an honest negative result:} L1 associativity is confirmed
cleanly this way on every machine attempted -- 8-way on three x86 machines spanning two
vendors/generations (Sunbird, Upgrade, Charnwood), 4-way on Thunderbird (AArch64,
Neoverse~N1), and a less-certain 12-way on Artemisia's larger 48\,KiB L1D. \textbf{L2 and
LLC associativity are not resolved by this method.} On every one of five machines tried,
byte-capacity candidates spanning up to a 32x range at the same nominal cache level break
at the \emph{same} small \texttt{num\_ways} (typically 9--12) regardless of the actual
byte capacity tested, and in two cases (Charnwood, Artemisia) the L2 and LLC curves are
numerically indistinguishable at every \texttt{num\_ways} despite a 32x--15x difference in
candidate capacity -- direct, on-machine evidence that a shared, capacity-independent
structure (leading hypothesis: DTLB aliasing, since every probed node lives on its own
4\,KiB page; a sliced-LLC hash function is a second, not-yet-ruled-out candidate) is what
these attempts actually measure, not the real cache level. The \texttt{--huge-pages}
control shown in Listing~\ref{lst:assoc} exists specifically to test the DTLB hypothesis by
collapsing the whole probe buffer onto one TLB entry, but has not yet been exercised on any
machine -- flagged here as the concrete next step, not attempted this cycle. A
derived-stride-scan technique (\texttt{scripts/run\_associativity\_stride\_scan.sh}) shows
more promise (self-consistent across several stride divisors on Upgrade's known-good L1)
but remains inconclusive at L2/LLC. No L2 or LLC associativity number in this report should
be read as machine-confirmed; see \texttt{CAPACITY\_RESULTS.md} and each machine's own
README for the full negative-result writeup.

\subsection{Cache Hit Latency}
\label{sec:hitlatency}

\textbf{What is varied:} load mode only (\texttt{dependent} vs.\ \texttt{independent}) at
one fixed footprint. \textbf{What is held constant:} the footprint itself, which must
already be confirmed (via Section~\ref{sec:capacity}'s boundaries) to sit entirely inside
one cache level -- this experiment infers nothing about capacity itself.
\textbf{What is measured:} median ticks/access, both load modes, both patterns.
Listing~\ref{lst:latency} implements this together with miss/next-level latency
(Section~\ref{sec:misslatency}), since both live in one file and are shown once here per
the reused-code convention.

\begin{lstlisting}[caption={Cache hit latency (this listing) and miss/next-level latency (Section~\ref{sec:misslatency} reuses this same file). Target properties: hit latency; miss/next-level latency. Architecture: portable common code. File: \texttt{main\_code/common/latency.c}, commit \texttt{e343732}.},label={lst:latency}]
int run_hit_latency_experiment(const struct hit_latency_config *cfg)
{
    size_t num_nodes = (size_t)(cfg->footprint_bytes / sizeof(struct node));
    if (num_nodes < 2) num_nodes = 2;

    uint64_t num_batches = (cfg->samples + cfg->batch_size - 1) / cfg->batch_size;
    if (num_batches < 1) num_batches = 1;

    double *batch_latencies = malloc(num_batches * sizeof(double));
    struct node *nodes = malloc(num_nodes * sizeof(struct node));
    if (batch_latencies == NULL || nodes == NULL) return 1;

    const char *pattern_name =
        (cfg->pattern == ACCESS_PATTERN_SEQUENTIAL) ? "sequential" : "random";
    const char *mode_name =
        (cfg->load_mode == LOAD_MODE_INDEPENDENT) ? "independent" : "dependent";

    if (cfg->pattern == ACCESS_PATTERN_SEQUENTIAL) {
        make_sequential_cycle(nodes, num_nodes);
    } else {
        make_random_cycle(nodes, num_nodes, cfg->seed);
    }
    /* Warm-up always via the dependent chain, regardless of the timed mode,
     * so both modes start from the same warmed-up residency. */
    for (int w = 0; w < cfg->warmup_passes; w++) chase(nodes, (uint64_t)num_nodes);

    printf("footprint_bytes,load_mode,pattern,batch_index,avg_ticks_per_access\n");

    if (cfg->load_mode == LOAD_MODE_INDEPENDENT) {
        size_t *order = (cfg->pattern == ACCESS_PATTERN_SEQUENTIAL)
            ? NULL /* identity order, built inline -- see full source */
            : make_shuffled_indices(num_nodes, cfg->seed);
        measure_independent_loads_batched(nodes, order, num_nodes, cfg->batch_size,
                                           num_batches, batch_latencies);
    } else {
        measure_dependency_chain_batched(nodes, cfg->batch_size, num_batches, batch_latencies);
    }

    for (uint64_t b = 0; b < num_batches; b++) {
        printf("%" PRIu64 ",%s,%s,%" PRIu64 ",%.4f\n",
               cfg->footprint_bytes, mode_name, pattern_name, b, batch_latencies[b]);
    }
    fflush(stdout);
    free(nodes); free(batch_latencies);
    return 0;
}

int run_miss_latency_experiment(const struct miss_latency_config *cfg)
{
    size_t target_nodes = (size_t)(cfg->target_bytes / sizeof(struct node));
    size_t evict_nodes = (size_t)(cfg->evict_bytes / sizeof(struct node));
    if (target_nodes < 2) target_nodes = 2;
    if (evict_nodes < 2) evict_nodes = 2;

    struct node *target = malloc(target_nodes * sizeof(struct node));
    struct node *evict = malloc(evict_nodes * sizeof(struct node));
    if (target == NULL || evict == NULL) return 1;

    const char *pattern_name =
        (cfg->pattern == ACCESS_PATTERN_SEQUENTIAL) ? "sequential" : "random";

    if (cfg->pattern == ACCESS_PATTERN_SEQUENTIAL) {
        make_sequential_cycle(target, target_nodes);
        make_sequential_cycle(evict, evict_nodes);
    } else {
        make_random_cycle(target, target_nodes, cfg->seed);
        make_random_cycle(evict, evict_nodes, cfg->seed + 1u);
    }
    for (int w = 0; w < cfg->warmup_passes; w++) {
        chase(target, (uint64_t)target_nodes);
        chase(evict, (uint64_t)evict_nodes);
    }

    printf("target_bytes,evict_bytes,pattern,trial_index,ticks\n");

    for (uint64_t trial = 0; trial < cfg->samples; trial++) {
        /* Untimed: re-establish target residency, then displace it by
         * walking the eviction-set cycle (evict_bytes must exceed the
         * source level's real capacity -- this is the ONLY eviction
         * mechanism in this codebase; there is no clflush anywhere). */
        chase(target, (uint64_t)target_nodes);
        chase(evict, (uint64_t)evict_nodes);

        /* Timed: exactly one dependent reload of the target line. */
        uint64_t t0 = timer_start();
        struct node *reloaded = target->next;
        uint64_t t1 = timer_stop();
        (void)reloaded;

        printf("%" PRIu64 ",%" PRIu64 ",%s,%" PRIu64 ",%" PRIu64 "\n",
               cfg->target_bytes, cfg->evict_bytes, pattern_name, trial,
               (uint64_t)(t1 - t0));
    }
    fflush(stdout);
    free(evict); free(target);
    return 0;
}

\subsection{Inclusion and Exclusion Behavior}
\label{sec:inclusion}

\textbf{What is varied:} nothing within a trial; the sweep is across level \emph{pairings}
(e.g.\ L1 vs.\ L2, L1 vs.\ LLC, L2 vs.\ LLC). \textbf{What is held constant:}
\texttt{target\_bytes} (a small, densely-packed set confirmed inside the UPPER level) and
an untouched \texttt{control} line at the identical sub-page offset (0); the eviction walk
uses a page-multiple stride (\texttt{evict\_stride\_bytes}, a multiple of 4096) so every
eviction node shares one fixed sub-page offset (\texttt{evict\_offset\_bytes}, default
2048) different from the target/control's own offset -- this is what lets the walk
structurally avoid the target's own upper-level set while still spanning enough distinct
pages to pressure the bigger LOWER level. \textbf{What is measured:} per-trial single-shot
reload latency for both the target and the control channel.

\begin{lstlisting}[caption={Inclusion/exclusion behavior. Target property: inclusion policy between an upper (inner) and lower (outer) cache level. Architecture: portable common code. File: \texttt{main\_code/common/inclusion\_policy.c}, commit \texttt{7be6dac}.},label={lst:inclusion}]
int run_inclusion_policy_experiment(const struct inclusion_policy_config *cfg)
{
    size_t target_nodes = (size_t)(cfg->target_bytes / sizeof(struct node));
    size_t evict_nodes = (size_t)(cfg->evict_bytes / cfg->evict_stride_bytes);
    if (target_nodes < 2) target_nodes = 2;
    if (evict_nodes < 2) evict_nodes = 2;

    /* Target and control: densely packed, page-aligned (offset 0), two
     * independent buffers so control's residency can never be disturbed
     * by anything done to target's own memory. */
    struct node *target = NULL, *control = NULL;
    posix_memalign((void **)&target, 4096u, target_nodes * sizeof(struct node));
    posix_memalign((void **)&control, 4096u, target_nodes * sizeof(struct node));
    if (target == NULL || control == NULL) return 1;

    /* Eviction buffer: one node every evict_stride_bytes (a page multiple),
     * offset evict_offset_bytes past a fresh page-aligned allocation, so
     * every eviction node shares a fixed sub-page byte position different
     * from target/control's own (0) -- structurally avoids the target's own
     * set PROVIDED the upper level's index fits within one page (true for
     * a typical L1; not for an L2-or-bigger target). */
    uint64_t evict_buffer_bytes =
        (uint64_t)(evict_nodes - 1) * cfg->evict_stride_bytes + sizeof(struct node);
    uint64_t evict_alloc_bytes = evict_buffer_bytes + cfg->evict_offset_bytes;
    void *evict_alloc = NULL;
    posix_memalign(&evict_alloc, 4096u, (size_t)evict_alloc_bytes);
    if (evict_alloc == NULL) { free(control); free(target); return 1; }
    void *evict_base = (void *)((uint8_t *)evict_alloc + cfg->evict_offset_bytes);

    const char *pattern_name =
        (cfg->pattern == ACCESS_PATTERN_SEQUENTIAL) ? "sequential" : "random";

    if (cfg->pattern == ACCESS_PATTERN_SEQUENTIAL) {
        make_sequential_cycle(target, target_nodes);
        make_sequential_cycle(control, target_nodes);
        make_sequential_cycle_strided(evict_base, evict_nodes, (size_t)cfg->evict_stride_bytes);
    } else {
        make_random_cycle(target, target_nodes, cfg->seed);
        make_random_cycle(control, target_nodes, cfg->seed + 1u);
        make_random_cycle_strided(evict_base, evict_nodes, (size_t)cfg->evict_stride_bytes,
                                   cfg->seed + 2u);
    }
    for (int w = 0; w < cfg->warmup_passes; w++) {
        chase(target, (uint64_t)target_nodes);
        chase(control, (uint64_t)target_nodes);
        chase(evict_base, (uint64_t)evict_nodes);
    }

    printf("target_bytes,evict_bytes,evict_stride_bytes,evict_offset_bytes,pattern,channel,trial_index,ticks\n");

    for (uint64_t trial = 0; trial < cfg->samples; trial++) {
        /* Untimed: refresh target/control residency, displace via the
         * page-offset eviction walk (only eviction mechanism -- no clflush). */
        chase(target, (uint64_t)target_nodes);
        chase(control, (uint64_t)target_nodes);
        chase(evict_base, (uint64_t)evict_nodes);

        /* Timed: exactly one dependent reload of each. */
        uint64_t t0 = timer_start();
        struct node *r_target = target->next;
        uint64_t t1 = timer_stop();
        uint64_t t2 = timer_start();
        struct node *r_control = control->next;
        uint64_t t3 = timer_stop();
        (void)r_target; (void)r_control;

        printf("%" PRIu64 ",%" PRIu64 ",%" PRIu64 ",%" PRIu64 ",%s,target,%" PRIu64 ",%" PRIu64 "\n",
               cfg->target_bytes, cfg->evict_bytes, cfg->evict_stride_bytes,
               cfg->evict_offset_bytes, pattern_name, trial, (uint64_t)(t1 - t0));
        printf("%" PRIu64 ",%" PRIu64 ",%" PRIu64 ",%" PRIu64 ",%s,control,%" PRIu64 ",%" PRIu64 "\n",
               cfg->target_bytes, cfg->evict_bytes, cfg->evict_stride_bytes,
               cfg->evict_offset_bytes, pattern_name, trial, (uint64_t)(t3 - t2));
    }
    fflush(stdout);
    free(evict_alloc); free(control); free(target);
    return 0;
}
\end{lstlisting}

\textbf{Known limitation, stated directly in the source:} the avoidance guarantee (the
eviction walk structurally cannot land on the target's own set) is proven to hold only when
the upper level's entire set-index fits within one 4\,KiB page -- true for a typical
32--64\,KiB, 8-way L1 (confirmed to fit exactly, e.g.\ Sunbird's 64 sets $\times$ 64\,B
lines = 12 index+offset bits), only \emph{approximately} true for a larger L1 with more
index bits (Thunderbird's 65{,}536\,B/4-way/256-set L1 needs 14 bits, 2 more than one page
holds), and essentially never true for an L2-or-bigger target. Pairings that use an L2
target (L2\_vs\_LLC) therefore carry the least confidence of any pairing on every machine
and are reported as leans, not firm calls. A second, independently discovered failure mode
surfaced once all eight machines were run: on Charnwood, both LLC-scale pairings' own
\emph{control} channel -- which is never touched by the eviction walk and should read
hit-speed on nearly every trial regardless of this machine's real inclusion policy --

\begin{enumerate}
\item[1.] L1D line size is 64\,B on all 8 machines with no exceptions across the full 2014--2023
span. L1D capacity (32\,KiB) and associativity (8-way) are likewise constant on 6 of 8 machines;
Thunderbird (Arm) and Artemisia (48\,KiB/12-way) are the only deviations. L1-vs-L2 non-inclusion
is stable across 6 of 8 machines with the remaining 2 leaning the same direction, the most
consistent architectural finding in this dataset.

\item[2.] L2 capacity per core is the one quantity with a clear, monotonic growth trend: 256\,KiB
(2014--2019) to 512\,KiB (2019) to 1\,MiB (2020) to 2\,MiB (2023), an exact 8$\times$ increase
over 9 years (Fig.~\ref{fig:chrono-l2cap}). The growth is stepwise, not smooth: five flat years
followed by three rapid doublings, not a continuously compounding trend.

\item[3.] LLC hit latency broadly grows with capacity (Ookay: 21\,ns at 8\,MiB; Sunbird: 23\,ns at
30\,MiB; Artemisia: 47\,ns at 52.5\,MiB), consistent with the expected wire-delay/capacity
tradeoff, but not cleanly monotonic across all 8: Upgrade reads 48\,ns at only 12\,MiB, higher
than Artemisia's much larger cache, an inversion we do not smooth over. DRAM latency does not
track CPU generation cleanly either: Artemisia (2023, dual-socket) is highest at 153\,ns, plausibly
a NUMA/platform effect rather than a memory-technology one, since several older single-socket
desktop parts (Sunbird, Ookay, Upgrade, Crux) all cluster tighter around 79--83\,ns despite being
4--9 years older.

\item[4.] Trends are better explained by server-vs-desktop class than by vendor or year alone.
Sunbird (2014, server) already has a larger LLC than every desktop part measured through 2019.
AMD's LLC sharing granularity (2 cores per CCX slice on Skylark) and Arm's LLC design (one SLC
shared by all 80 SoC cores on Thunderbird) are vendor/ISA-specific chiplet or fabric choices, not
points on a shared generational curve with the Intel parts.

\item[5.] L2 capacity per core (Fig.~\ref{fig:chrono-l2cap}) most resembles Moore's style of
trend: monotonic, an integer power-of-two multiple across the full span, and the only quantity
this fleet's data supports fitting an exponential to. Fit as $C(t) = C_0 \cdot 2^{(t-t_0)/\tau}$
using the 2014 and 2023 endpoints only ($C_0=256$\,KiB, $8\times$ over 9 years) gives a clean fit
at those two points by construction; a least-squares fit across all 8 points would fit poorly
because the trend is a step function, not smooth, so the exponential is an end-to-end summary, not
a validated per-year model.

\item[6.] Using the two endpoints above, L2 capacity per core has a doubling time of
$9/\log_2(8) = 3$ years. No other measured quantity shows exponential growth clean enough to quote
a doubling time; LLC capacity and associativity are better described as class-dependent step
changes with no consistent per-year slope, and line size and L1D capacity/associativity are
reported as constant (item 1), not growing.

\item[7.] The lab-only prediction was frozen and tagged \texttt{predictions-frozen} in
\texttt{PREDICTION\_FREEZE.md} on 2026-09-14, before any Hazel cache experiment ran (Hazel access
was only exercised via a non-cache build/access-check job on the \texttt{haswell} constraint, which
this project's phase discipline explicitly permits pre-freeze). Evaluating the frozen prediction
against held-out Hazel measurements is still pending -- the full 1,000,000-sample cache suite has
not run on Hazel yet -- and this item will be completed once those results exist. Using only the 8
lab machines, we extend the L2-capacity-per-core
doubling model from item 6 ($\tau=3$ years) 5 years beyond the newest measured system (Artemisia,
2023) to $\sim$2028: $2\,\text{MiB} \times 2^{5/3} \approx 6.3$--$6.7$\,MiB per core. Given the
trend is a step function rather than smooth (item 2), we report a wide uncertainty range of
roughly 4--10\,MiB per core rather than a tight interval around the point estimate. This
prediction could fail if the next generation's core-count growth outpaces per-core cache scaling
(a common tradeoff when die area is fixed), if a vendor shifts strategy toward a larger shared LLC
instead of per-core L2, or if the sampled generation is a server part whose class-driven capacity
(item 4) does not follow the desktop/server mix observed in this fleet.

\item[8.] The evidence here is far weaker than Moore's original observation: Moore's trend held
smoothly across many more generations and a single scaling technology (transistor count), while
this fleet's 8 machines over 9 years show one plausible doubling trend (L2 capacity per core,
step-like rather than smooth), several deliberately-constant quantities (L1D line size, largely
L1D capacity/associativity), and several quantities dominated by non-chronological factors
(LLC capacity and sharing domain, dominated by server/desktop class and vendor chiplet design).
We do not claim a capacity-doubling law with Moore's original confidence; at most, a modest,
step-wise L2-capacity growth claim is defensible from this data.
\end{enumerate}

\subsection{9.1 Your Team's Cache Laws and Future Scaling Walls}

Two named laws are formulated below, using both team members' surnames (Chen, Ngo) per the

\subsubsection*{Law 1: Chen--Ngo Cache Capacity Doubling Law}

\textbf{Statement.} Per-core L2 cache capacity on the team's lab machines grows with processor
introduction year via a step-doubling trend, doubling on average every 3 years across the 2014--2023
span sampled.

\textbf{Quantitative rule.} $C(t) = 256\,\text{KiB} \cdot 2^{(t - 2014)/\tau}$, with $\tau = 3$ years,
fit from the dataset's two chronological endpoints (Sunbird, 2014, 256\,KiB $\to$ Artemisia, 2023,
2\,MiB -- an exact $8\times$ increase over 9 years). The underlying data is a step function, not a
smooth curve: flat at 256\,KiB for five years (2014--2019: Sunbird, Charnwood, Ookay, Upgrade, Crux),
then three back-to-back doublings in four years (512\,KiB -- Skylark, 2019; 1\,MiB -- Thunderbird,
2020; 2\,MiB -- Artemisia, 2023). The fitted $\tau$ is an end-to-end summary between two endpoints, not
a per-year validated slope (see \S\ref{sec:evolution}, items 2, 5, 6, for the full derivation).

\textbf{Scope/domain.} 8 machines, 2014--2023, pooled across vendor/ISA (6 Intel x86-64, 1 AMD
x86-64 [Skylark], 1 Arm AArch64 [Thunderbird]) and pooled across desktop/server class. Not
vendor-specific: the two fitted endpoints are both Intel, but the two intermediate step points come
from AMD and Arm parts, so the doubling time is not read off a single vendor's roadmap alone. Does not
imply the trend holds beyond 2023, outside this 8-machine sample, or for a machine class not
represented in this fleet.

\subsubsection*{Law 2: Chen--Ngo Cache Invariance Law}

\textbf{Statement.} L1D cache capacity, associativity, and line size on the team's lab machines are
approximately invariant across a decade of processor generations and three vendors/ISAs, rather than
scaling with year the way L2 capacity does.

\textbf{Quantitative rule.} Line size: 64\,B on 8 of 8 machines (2014--2023), zero exceptions. L1D
capacity: 32,768\,B (32\,KiB) on 6 of 8 machines. L1D associativity: 8-way on 6 of 8 machines. The
same two machines account for both deviations -- Thunderbird (Arm, 2020: 64\,KiB, 4-way) and Artemisia
(Intel Sapphire Rapids, 2023: 48\,KiB, 12-way) -- and they deviate in different directions/magnitudes
from each other despite Artemisia being the newer machine, i.e.\ the deviations themselves show no
chronological trend.

\textbf{Scope/domain.} Same 8-machine, 2014--2023, cross-vendor/ISA pool as Law 1. The invariance
claim is majority-case (6 of 8), not universal, and is stated as approximate; it is known not to hold
for the team's one Arm machine or its newest/largest-L1D Intel Xeon, and should not be assumed to hold
for machine classes outside this fleet.

\subsubsection*{Future Scaling Walls}

\textbf{Wall for Law 1 (capacity doubling).} The 3-year doubling time is fit from a fleet that was flat
for 5 years and then doubled three times in 4 years -- i.e.\ the model is extrapolating a recent burst,
not a long-observed steady rate, and two independent physical constraints could break it going
forward. First, a \emph{latency wall}: \S\ref{sec:evolution} item 3 already shows LLC hit latency
broadly growing with LLC capacity across this fleet; the same wire-delay/capacity tradeoff applies to
L2, so continuing to double L2 capacity every 3 years would eventually push L2 hit latency toward
today's LLC latency range, eroding the two-level (L2/LLC) split's purpose unless vendors insert an
additional mid-level cache -- a redesign, not a continuation of the same curve. Second, a
\emph{fabrication wall}: this project's own data cannot observe process-node effects directly (Phase I
is timing-only), but the fitted doublings land almost entirely in the fleet's more recent, smaller-node
machines (Skylark and Thunderbird at 7\,nm, Artemisia at 10\,nm/Intel~7), while SRAM cell density is
publicly known to scale much more slowly than logic density below roughly 7\,nm -- a hard limit this
project's data is consistent with but cannot independently confirm, flagged here as an external risk
to the extrapolation rather than a lab finding. Third, a \emph{core-count wall}: per-core L2 capacity
competes with core count for the same fixed die-area/power budget (already noted as a risk in
\S\ref{sec:evolution} item 7); if future generations grow core counts faster than die area, per-core L2
capacity could flatten or reverse even while total on-die SRAM keeps growing.

\medskip

\noindent\textbf{Wall for Law 2 (invariance).} Unlike Law 1, this law describes a quantity that appears to have
\emph{already} hit its scaling wall rather than one that will hit it in the future: L1D capacity and
associativity are bounded by a strict load-to-use latency budget (commonly $\leq$4 cycles in modern
designs), and growing L1D physically increases wire delay and tag-comparator fan-in in a way that would
violate that budget -- consistent with why L1D has not grown across 9 years and 3 vendors on 6 of 8
machines even as transistor budgets elsewhere on the same dies have grown by orders of magnitude. The
two deviations show the wall is soft, not absolute: a different microarchitectural latency budget
(Arm's Neoverse~N1 core design; Intel's newest server core) can push through it by roughly
50--100\,\%, but not by the multiplicative factors Law 1's L2 trend shows over the same span. The
practical implication for future generations, including any that show a materially larger L1D than
32\,KiB, is that this project's own timing-only method predicts it should also show a
correspondingly \emph{higher} L1D hit-latency in ticks (not a free capacity increase) -- a testable,
falsifiable consequence of this law that a future Hazel or successor-fleet measurement could check
directly against the frozen 32,768\,B / 8-way / 64\,B prediction above.

The held-out evaluation for both laws (measured Hazel value, error, and supported/weakened/falsified
verdict) is recorded in \texttt{PREDICTION\_FREEZE.md}'s ``Held-Out Evaluation'' table once the Hazel
cache-experiment suite has run; per that file's own rule, Hazel points are never used to refit either
law above.

Item 7's forward-looking capacity prediction (the general Section~\ref{sec:evolution} extrapolation,
distinct from the two named laws above) is derived and stated in full in Section~\ref{sec:evolution}
above, alongside the rest of the Section 9 interpretation items, since it follows directly from the
same doubling-time model (item 6). The held-out evaluation half of item 7 is likewise pending Hazel
data and will be added to that item once Hazel measurements are collected.
