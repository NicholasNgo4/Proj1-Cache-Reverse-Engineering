- **L1 = 8-way: clean, matches the team-wide result.** Single sharp knee (flat ~7.6 ticks/access through num_ways=8, jump to ~19-23 at 9+), 0 disagreement across base + 2 repeats, both patterns track together. Same shape and same estimate as Sunbird's and Upgrade's independently hand-confirmed L1 = 8-way results (see `CLAUDE.md`'s associativity section). This is the one level on this machine where the result should be trusted at face value.
- **L2 and LLC did NOT produce trustworthy independent numbers — new, unusually direct evidence for the team's already-documented DTLB/small-structure confound.** Both curves are multi-step staircases, not single knees: a first jump at num_ways=4 (7.56 -> 15.6 ticks), a second, sharper jump at num_ways=9 (15.6 -> 21.9 ticks) — the same num_ways=9 anomaly CLAUDE.md documents recurring across every Sunbird large-stride candidate tried — then a gradual, noisy climb from ~num_ways=24 onward (25-45% run-to-run spread per the pipeline's own overlap warnings, consistent with genuine measurement noise at that depth rather than a third real knee). `detect_associativity.py` only reports the first knee, hence "4" for both levels.
  - **The striking new fact: L2 (256 KiB stride) and LLC (8 MiB stride) — a 32x difference in the candidate capacity — produce median latencies that agree to within ~0.05 ticks/access at every num_ways from 2 through 23** (e.g. 21.892 vs. 21.892 at num_ways=9, 21.898 vs. 21.872 at num_ways=20; see the two levels' `base_random_summary_20260912T225012Z.csv` files). Two genuinely different cache levels, being probed at their own real distinct capacities, have no reason to produce numerically indistinguishable curves — this is direct, on-this-machine evidence that both "L2" and "LLC" runs are measuring the same small, capacity-independent structure (most likely the DTLB, per CLAUDE.md's leading hypothesis: `cache_bytes` is always a multiple of the 4096-byte page size, so this experiment always exercises the DTLB too, not just whichever data-cache level it's aimed at), not the real L2 or LLC associativity.
  - **Conclusion: treat "L2 associativity = 4" and "LLC associativity = 4" for Charnwood as NOT resolved** — they are reproducible (0 spread across repeats) but reproducibly wrong in the sense of not reflecting the cache level nominally under test. This mirrors, and adds a cleaner same-machine A/B comparison to, the dead end CLAUDE.md already documents from Sunbird (10 of 13 large-stride candidates across a 27x byte range breaking at the same num_ways=10) and Upgrade (a two-step staircase with the same "~9" second step). Per that writeup, simply trying more candidate byte values is very unlikely to help; the "derived-stride scan" technique in `scripts/run_associativity_stride_scan.sh` (validated on Upgrade's L1, inconclusive on Upgrade's L2/LLC) is the only currently-proposed way forward, and hasn't been tried on this machine.
- **Known limitations / open questions specific to this run:**
  1. The L2 (262,144 B) and LLC (8,388,608 B) `cache_bytes` values were taken from `CAPACITY_RESULTS.md`'s cross-machine table, not from a hand-confirmed boundary in Charnwood's own capacity data — that data explicitly flags the ~1.83-11.31 MiB region as contaminated/unresolved (see `capacity/` section above). Even setting aside the confound finding above, this run cannot be treated as validating those specific byte values as Charnwood's real L2/LLC capacities.
  2. Because of finding above (L2 and LLC curves being numerically indistinguishable through num_ways=23), this run cannot currently distinguish whether Charnwood's real L2 capacity is actually 262,144 B, whether its real LLC capacity is actually ~8 MiB, or either — the method is bottlenecked on the shared confound before capacity choice even matters, consistent with CLAUDE.md's Sunbird conclusion ("no candidate byte value fixes it... something with ~9 slots saturates long before any real, larger cache set would").
  3. Per Phase I discipline, no hardware topology lookup (`cpuid`, `/proc/cpuinfo` cache fields, full `lscpu`) was used to investigate this further — see CLAUDE.md's "Phase I discipline caveat" for why that specific line of investigation was already tried and reverted on Sunbird.

- **Result (dependent, random pattern, n=1000 each) — a clean, monotonically increasing 4-tier ladder: L1 ≈ 9.55 (base) / ≈7.98 (rep1+rep2 avg) ticks, L2 ≈ 22.12 (base) / ≈17.27 (rep1+rep2 avg) ticks, LLC ≈ 106.9-109.1 ticks (all 3 runs agree), DRAM ≈ 394.6-394.8 ticks (all 3 runs agree).**
- **Base-run cold-start anomaly found and investigated (not a data-quality problem, a genuine P-state effect):** the L1 and L2 **base** runs measured systematically higher than their own rep1/rep2 (L1: every one of 1000 batches in the base run sits >9.0 ticks, vs. 994/1000 batches <9.0 in rep1; L2 base median 22.12 vs. rep1/rep2 17.46/17.07 — a persistent, run-long elevation, not a brief startup transient decaying within the run, confirmed by inspecting the raw per-batch CSV directly). LLC and DRAM (run 3rd and 4th, after L1/L2's 6 combined runs had already kept the core busy) show no such gap between base and repeats. This is the same category of finding CLAUDE.md documents for Artemisia's P-state/turbo-related sub-48 KiB bimodality: the very first workload run after the core sits at whatever P-state the OS left it in, and small/fast footprints (L1, L2) finish before the core has necessarily settled into steady-state turbo, while larger/slower footprints (LLC, DRAM) — and any run that comes after several thousand already-executed batches — don't show it. **The L1/L2 numbers reported above use the rep1+rep2 average as the trustworthy figure; the base-run medians are listed for transparency but should not be cited as this machine's L1/L2 hit latency.**
- **Diagnostic-control check (independent < dependent, required by PROJECT 1.pdf item 5):** held at every level for the `random` pattern (L1: 7.54 vs 8.51; L2: 9.65 vs 18.88; LLC: 36.03 vs 107.86; DRAM: 60.19 vs 394.76 — all "[expected]"), and for `sequential` at L1/L2/DRAM. **One UNEXPECTED flag, investigated:** LLC/sequential showed independent >= dependent (8.28 vs 8.10 combined). Checked per-run (not just the combined/averaged figure the pipeline flags on): base 8.398 vs 8.126, rep1 8.246 vs 8.088, rep2 8.190 vs 8.088 — the flip is small (2-3%) but consistent across all 3 independent runs, so it isn't a one-off noise spike. Root cause: at the `sequential` pattern, EVERY level's hit-latency numbers cluster in the same narrow ~7.4-8.7 ticks/access band regardless of footprint (L1 through DRAM), because hardware prefetching hides essentially all of the real memory-hierarchy latency difference when access order is sequential — unlike `random`, where the four levels separate by 10x-40x. With the real signal that thoroughly hidden, `independent` vs. `dependent` for `sequential` is comparing two numbers that are both dominated by prefetch/streaming bandwidth rather than by memory-level-parallelism-vs-not, so a few-percent, sign-flippable gap is expected measurement noise rather than a violation of the diagnostic control's actual claim (which is about hiding latency behind MLP, not about ordering two near-identical bandwidth-bound numbers). Treated as investigated-and-explained, not a reason to distrust the dataset — the `random`-pattern results (the actual reportable hit-latency numbers) show the expected behavior cleanly at every level.
